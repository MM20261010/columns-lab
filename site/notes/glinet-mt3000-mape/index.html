GL.iNet純正OP25のGL-MT3000で、BIGLOBE系MAP-E接続を設定した話

AdGuard Homeに興味はあるけど「日本のIPv4 over IPv6でつながるの？」と不安な人へ。Beryl AX（GL-MT3000）にメーカー提供のOP25系ファームウェアを導入し、BIGLOBE系MAP-Eで接続するまでに経験した設定・つまずき・確認方法を一台の実機記録としてまとめた。

記録整理：2026年10月22日 ／ 実機：GL-MT3000（Beryl AX） ／ メーカー提供の4.9.1-op25系を検証 ／ 接続方式：BIGLOBE IPv6オプション相当のMAP-E ／ Flint 4は未検証

先に大事なこと：これは一台の実機検証で、BIGLOBEの全契約や他機種での動作保証ではない。契約者に割り当てられるIPv6プレフィックスやPSIDなどの値はコピーしないこと。ネットを使える状態に戻せるよう、動作中のファームウェアと設定のバックアップを準備してから作業しよう。メーカー配布OP25系と、OpenWrt本家を直接導入した環境は同一ではない。

最初に：BIGLOBEの「v6プラス」と「IPv6オプション」は同じ名前ではない

BIGLOBE公式によれば、両者は仕組みが同等でも、v6プラスはJPIX社側の設備、IPv6オプションはBIGLOBE側の設備を利用する別サービス。どちらもMAP-E系でも、設定ルールが同一だと決めつけないでほしい。BIGLOBE公式FAQ：v6プラスとIPv6オプションの違い

今回の記録値はBIGLOBE IPv6オプション相当のルールと一致したもの。契約書や管理画面でサービス名を正式に確認した記録はないため、「自分の回線は公式にv6プラス契約だった」とは断定しない。v6プラス利用者にも切り分け方は参考になるが、ルールの流用はしないこと。

1. GL.iNetの何を使った？ 作業前の確認

利用機材はGL.iNet GL-MT3000（Beryl AX）。従来のメーカー提供4.8.3-op24／OpenWrt 24系から、メーカー配布の4.9.1-op25系（OpenWrt 25系）へ、設定を引き継がずクリーン導入した。一般の安定版4.9.0などとは異なるOP25系列のファームウェアの話。最新配布状況とリリース区分はGL.iNet公式ダウンロードセンターで確認してほしい。

移行中は、当初WAN6でIPv6プレフィックスを取得できない場面や、ルーター自身はIPv6通信できてもLAN端末側へグローバルIPv6がうまく配布されない状態、MAP-Eがつながらない状態、ページ表示が異常に遅い状態を順に経験した。原因は一つではなく、設定を一度に触るほど切り分けが難しくなった。

大切なのは「ルーターがIPv6で通信できる」「スマホがLANからIPv6で通信できる」「IPv4サイトも開ける」を別々に確かめること。 GUIで設定しても、細かいLuCI項目に踏み込む必要があった。GL.iNet公式のアップグレード・バックアップ手順も先に読んでおきたい。

2. 接続までに実際に確認した順序

  1. 逃げ道を確保：OP24で動作した設定をバックアップ。必要なら別ルーターを一時的な親機に使い、ネット回線への復帰手段を残す。
  2. メーカー提供OP25をクリーン導入：「Keep Settings」でOP24設定を持ち込まず、公式配布イメージから導入。WAN6はDHCPv6として、最初にIPv6接続と取得プレフィックスを確認した。
  3. LuCIでWAN側をMAP-Eに設定：MAPルールを入力してトンネルの基点はwan6に。WAN詳細の「従来のMAPを使用」を有効にしたら接続できた。従来のexport LEGACY=1を追加する必要はなかった。
  4. Firewallを確認：WANゾーンのMasquerade（マスカレード）とMSSクランプを確認。検証時はNAT6も導入したが、NAT6が必須という意味ではない。構成の違う人が理由なく入れるのは避けたい。
  5. MTU調整：MAPトンネルをMTU 1460で調整し、ページ表示が著しく遅い症状の切り分けを行った。回線差があるため1460を万能値とはしない。
  6. LAN側IPv6：LuCIでLANへの/64プレフィックス配布、RA／DHCPv6サーバーモードを確認。sourcefilter=0やra_default=1などの追加調整は、IPv6不調を切り分けたこの環境固有の検証設定として扱った。

LuCIの表記や初期値はFWによって違う。上記は実機での流れで、すべての項目が普遍的な推奨設定とは限らない。変更は一項目ずつ。うまくいかなくなったら直前の値へ戻し、別の原因を探る。

4. IPv6がルーターまで来ているのに端末で使えない

途中で特に厄介だったのは、GL-MT3000自身ではIPv6接続できても、LAN端末にはfe80:: や fd00:: のアドレスしか見えず、期待したグローバルIPv6の割り当てや経路が確認できない状態だったこと。リンクローカル／ULAのアドレスが表示されるだけでは、インターネットIPv6の成功を意味しない。

当時の切り分けでは、LANのRAサーバー、DHCPv6サーバー、SLAAC、LANプレフィックス長64、wan6.sourcefilter=0、dhcp.lan.ra_default=1、NDP Proxy無効を確認した。これらは検証環境で最終的に使った設定であり、すべてを他環境で一律に変更する推奨ではない。

odhcpdのログレベルに関する注意

当時はodhcpd.loglevel=7とサービス再起動でRA関連の挙動が改善した。OpenWrtのodhcpdでも2026年に「ログレベル7でないとRAが正常送信されない」とする不具合報告（Issue #388）がある。ただし、報告環境と今回のGL-MT3000は同一ではなく、原因が確定したわけではない。更新済みodhcpdでは再現しない可能性もある。

実際に試したコマンド（管理者権限のSSHで実行）

MAP-EとWAN6の設定を確認した後、LAN端末へIPv6の広告が届かない症状に対して次を試した。設定変更前の値を控えたうえで、必要な場合だけ実行してほしい。通信中の端末では短時間の再接続が起きる可能性がある。

# 最初は確認のみ：元の設定値を控える
uci -q get dhcp.odhcpd.loglevel
uci show dhcp.lan
ifstatus wan6

# 当時行った回避策（設定を変更する）
uci set dhcp.odhcpd.loglevel='7'
uci commit dhcp
/etc/init.d/odhcpd restart

# 再起動後のログを確認
logread | grep odhcpd | tail -n 30

この3行の変更コマンドは当時の作業記録に残っているもの。「7」が必ず必要と証明したわけではない。OpenWrtのIssue #388（別環境の類似報告）も参考になるが、そちらはOpenWrt 25.12.0での報告でありGL.iNet提供OP25と同じバージョンや原因を意味しない。

スマートフォンからの確認

Wi-Fiをいったん再接続し、端末のIPv6アドレスとデフォルトルートを確認する。fd00:から始まるULAやfe80:から始まるリンクローカルアドレスが見えるだけでは成功とはいえない。ISP由来のグローバルIPv6が使え、https://ipv6.google.com/などへ実際に到達することを確認する。logreadにRA送信に関する記録があれば切り分けに役立つ。

症状が直らない・元に戻すとき

直らなければログレベルだけに固執せず、WAN6のPD、LANのRA設定、IPv6ルート、odhcpdのバージョンを確認する。元のログレベルが数値4など明示設定されていた場合はその値へ復元し、元々項目がなかった場合だけ次のように未設定へ戻す。

# 「変更前にloglevelが未設定だった」場合の復元例
uci -q delete dhcp.odhcpd.loglevel
uci commit dhcp
/etc/init.d/odhcpd restart

変更前の値が4などであれば削除ではなくuci set dhcp.odhcpd.loglevel='元の値'で復元し、commitと再起動を行う。デバッグログが増えるので、症状が解消した後も設定を固定すべきかは修正版への更新状況と動作を見て判断しよう。

まずは取得プレフィックス・RAの送信状況・サービスログを見てから判断する。ログレベル7は詳細なデバッグ記録が増えるため、恒久設定にするかはファームウェアの修正状況とログ容量を確認したい。NAT6やsourcefilter変更もセキュリティ・経路設計に影響し得るので、原因不明のまままとめて適用しない。

5. 最後に確認したこと

  1. WAN6がIPv6情報を取得し、ルーター自身からIPv6の宛先に到達できる。
  2. MAP-E経由でIPv4のWebサイトを開ける。
  3. スマートフォンなどLAN端末からもIPv4/IPv6の両方に到達できる。
  4. IPv6対応ページを開く際、極端な待ち時間や一部サイトだけの停止がない。
  5. ルーター再起動後も取得・ルーティング・RAが復帰するかを別途確認する。

当時の実機では「ニチバンのサイト」や ipv6.google.com を用いて疎通を確認した。少数サイトの閲覧成功は、全環境の安定性・長期間の再起動耐性を証明するものではない。

6. AdGuard Homeは設定が難しい？

GL.iNetを買う理由の一つが、ルーターに内蔵されたAdGuard Home。端末ごとにアプリを入れず、家じゅうのDNS問い合わせを元に広告・トラッキングドメインへのアクセスを減らせる。公式対応モデル表にはBeryl AXとFlint 4の両方が掲載されている。

始めるだけなら管理画面から

  1. GL.iNet管理画面へログインし、「APPLICATIONS → AdGuard Home」を開く。
  2. 有効化して「Apply」。DNS問い合わせ数やブロックの統計が表示される。
  3. 必要なら「Settings Page」へ進み、フィルタや許可リストを調整。最初から大量のフィルタを積まず、使うアプリに支障がないか確かめる。

ここはネット接続を完成させてから設定するのがおすすめ。 最初からMAP-EとAdGuard Homeを同時に触ると、つながらない原因が回線かDNSか分からなくなる。動作に問題が出ればまずAdGuard Home側の設定・ログを確認し、切り分けのため一時無効化する。

実用的な場面

  • PCやスマートフォンだけでなく、アプリを入れにくいスマートTV、ゲーム機、IoT機器にもネットワーク単位のフィルタリングを適用しやすい。ただし端末側が別DNSを使用すると適用されない場合がある。
  • ブロック数と問い合わせ先を管理画面で確認し、誤ブロックを見つけたらフィルタや許可リストを調整できる。
  • 家族や複数端末のDNSフィルタを、機器ごとに手動設定する負担を減らせる。

期待しすぎない方がいいこと

YouTubeの動画広告など、コンテンツと同じドメインから配信される広告はDNS方式だけでは基本的に除去できない。 アプリやブラウザーが独自DNSを利用するとフィルタを通らない場合もある。GL.iNet公式も、AdGuard HomeによるクライアントDNSの直接処理が、ドメイン別VPNポリシーやペアレンタルコントロールに影響し得ると注意している。

最初は控えめなフィルタ構成で通信への影響を観察し、Webサイトやアプリが壊れたらブロックログを確認。DNS保護と、ブラウザー拡張による要素非表示は役割が異なる。なお、「AdGuard Home Handle Client Requests」を有効にすると、公式案内ではドメインベースのVPNポリシーとペアレンタルコントロールが効かなくなる点にも注意。この節は公式機能の紹介であり、今回のOP25実機でAdGuard Home全機能を再試験した報告ではない。

7. Beryl AXからFlint 4へ。この設定は使える？

Beryl AX（GL-MT3000）は小型でOpenWrt設定を試しやすいWi-Fi 6ルーター。今回のBIGLOBE系MAP-E復旧を実機で確認したのはこの機種。

Flint 4（GL-BE14000）はWi-Fi 7、10GbEなどの高速有線インターフェースを備え、公式資料でAdGuard Home対応を確認できるホームルーター。家庭内端末が多く、ルーターにDNSフィルタも任せたい場合に製品検討の対象となる。

ただし、Flint 4で同じMAP-Eルール・Legacy MAP・odhcpd回避策が有効かは未検証。 特にOpenWrtの世代、ファームウェアの実装、ISPの割当条件が違えば手順を読み替える必要がある。Beryl AXの成功＝Flint 4の動作保証、とはしない。

このページの外部製品リンクはメーカー公式サイトへの通常リンクで、掲載準備時点でアフィリエイトリンク・報酬提携はない。製品の購入を推奨する前に、実際の回線方式・ファームウェア・機能対応を確認してほしい。

まとめ

今回の教訓は、MAP-Eの成否、WAN6のIPv6取得、LANへのRA/DHCPv6、MTU/MSS、DNSフィルタを一度にいじらず、順番に検証すること。実機で得た設定値は有力なヒントになるが、加入者固有の値や機種差まで消してくれる魔法の設定ではない。

本記事は個人の試行記録を整理したもので、GL.iNet、BIGLOBE、AdGuard各社の公式サポート記事ではない。仕様は変更されるため、必ず公式資料と現在の回線条件を優先してほしい。
