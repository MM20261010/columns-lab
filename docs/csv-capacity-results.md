# CSV出力膨張：測定と未公開の上限案

測定日: 2026-10-11（日本時間）。架空データのみ、Node.js v24.19.0、Workローカル環境。利用者のCSV/ファイル名は使わず送信・記録しない。端末をクラッシュさせる試験は行わない。

## 測定方法・結果

2ファイルで互いに異なる列名を用意し、全セルを短い固定値で埋める。入力は疎なままでも結合後は列の和集合に合わせた配列になる。gc後にV8のused_heap_sizeを測定。値は終了時の差でありピーク/全プロセスメモリではない。process.memoryUsageはこの環境でuv_resident_set_memory/ENOENTとなりRSSを取得できなかった。

| 現行コード：データ行 | 出力列 | データセル | 出力文字数 | 結合ms | 書出ms | 終了時heap増加MiB（丸め） |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2,000 | 21 | 42,000 | 106,074 | 2 | 6 | 5 |
| 10,000 | 41 | 410,000 | 1,030,154 | 14 | 33 | 13 |
| 20,000 | 61 | 1,220,000 | 3,060,234 | 65 | 214 | 27 |
| 20,000 | 121 | 2,420,000 | 6,060,474 | 61 | 180 | 64 |

単回の測定で、順序/JIT/GCの影響がある。大きいケースが必ず長時間になるという比較はできない。スマホ、DOM/Blob、文字コード復号、解析の全工程を含む値ではない。

## 修正案と利用者への影響

- 構文解析中にセル数を数え、上限を超えるセルを追加する前に停止。アプリ側で複数ファイルの入力合計を管理する。
- 列の和集合と行数から出力セル数を計算。入力値・引用符数・区切り・CRLF・元ファイル名の繰返し・数式保護分を数え、密な出力行を作る前に文字数の保守的な上界を計算する。UTF-16コード単位で、UTF-8のバイト数ではない。
- 書出時にも文字数を確認し、行のspreadを避ける。上限エラーで古い結果を保存しない。値を黙って切り捨てず、ファイル分割・不要列削除を案内する。
- 暫定案: 入力は各ファイル100,000データ行（空行含む）・合計500,000セル、出力は合計100,000データ行・ヘッダー込み500,000セル・256列・見積もり4,000,000文字。従来の10MiB/25MiBだけでは小さい入力の膨張を止められない。50列なら約9,999データ行、200列なら約2,499行がセル上限の目安で、文字数制限が先にかかる場合もある。
- 10,000行/41列の実測約13〜14MiBを含む規模を残し、それより大きい密出力を早期に止める保守的な製品方針。256列は2行/256列のコア処理を測定して通過を確認した候補。DOM/スマホの安全性の証拠ではない。400万文字も全端末の安全限界ではなく、既存の約606万文字ケースを制限する暫定候補。
- 以前使えた大きいCSVや多数列でも拒否される。上界計算は数式対策OFFや空欄が多い場合も余裕を見込むため、実際の出力より大きく見積もって拒否することがある。制限の緩和・出力モード別見積もりは別の判断事項。

## 中断と残る検証

現案の中断は解析セル上限、密出力前の判定、書出上限での例外停止。ユーザーが途中で押すキャンセルボタンは未実装。同期の解析/結合/保存の最中はUI操作で直ちに中断できない。入力バイト制限内でも長い単一フィールドの解析は残る。現案だけでフリーズがなくなると断定しない。

次の検証: 少数の長い値/多数の短い値/引用符/日本語/重なる列/空行・ヘッダーだけ、複数ファイル合計、保存時例外、DOM/Blobのピーク、スマホ実機。必要なら専用Worker＋明示キャンセル＋terminateを別PRで設計。CSVを第一者Worker内だけで処理し、外部通信しない。コピー/転送時のメモリ増加、古い結果の破棄も確認する。Workerは今回追加していない。

再現のコア例（本番で実行しない。各ケースは独立したローカルNodeで実行し、2,420,000セルを超えて増やさない）:

```js
// node --expose-gc --max-old-space-size=256 benchmark.js
const T=require('./site/assets/csv-core.js'),v8=require('node:v8');
global.gc();
const before=v8.getHeapStatistics().used_heap_size;
const n=5000,k=20;
const tables=['a','b'].map(name=>({name,rows:[
  Array.from({length:k},(_,i)=>name+i),
  ...Array.from({length:n},()=>Array(k).fill('123'))
]}));
const start=performance.now();
const out=T.mergeTables(tables);
const mid=performance.now();
const result=T.writeCSV(out.columns,out.rows);
console.log({rows:out.total,columns:out.columns.length,characters:result.length,
  mergeMs:mid-start,writeMs:performance.now()-mid,
  heapDeltaMiB:(v8.getHeapStatistics().used_heap_size-before)/1048576});
```

このコードは固定架空データで、内容・名前をログに出さない。数式対策PRと上限PRは同じcore/test/説明ファイルを触るので、順番に統合して両方のテストを再実行する必要がある。スマホ未検証のため上限PRはDraft・未公開を維持する。

## 行数の追加測定と上限判断

列名が同じ1列×2ファイル（元ファイル名あり）の細いデータでも、行配列の数がメモリに影響する。現案の行数上限追加前で測定: 20,000行/40,002セルは結合12ms・保存11ms・heap増加6MiB、100,000行/200,002セルは35ms・50ms・19MiB、200,000行/400,002セルは130ms・220ms・27MiB。単回・終了時差で、ピークではない。この観測から暫定100,000行も上限に加え、細いCSVの200,000行を許可し続けない方針とした。入力行制限は空行も数えるので、多数の空行を含むファイルも分割が必要。スマホで安全とはまだ言えず、公開前の実機検証が必要。
