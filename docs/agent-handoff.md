## 承認の境界

| 自律的に進める | 先に本人の承認・認証が必要 |
| --- | --- |
| 公開資料調査、既存権限の読み取り、架空データ試験、低リスク文書更新、修正案・PR作成 | 新しいOAuth権限・外部接続・Secrets・トークン、課金・契約、重要な外部操作、重大な公開動作変更 |

GPTによる再認証は行わない。既存プレビュー削除・自動プレビュー停止は本人対応と読み取り確認が完了。Analytics自動取得の追加権限は提案段階。既存権限を維持する選択も可能。秘密情報をチャット・コード・公開ログに貼らない。Account IDは秘密鍵ではないが、公開記録に不要な識別情報を増やさず、認証済み接続または本人の既存文脈から取得して引数に明示する。

## 戦略チャット・Work・将来の開発担当の運用

戦略チャットは優先順位・監査・承認判断、Work/開発担当は証拠収集・実装・テスト・PRを担当する。引き継ぎの一次情報はGitHub。新しい担当は本ファイル→月次記録→該当監査を読み、mainの最新状態を取得してから作業する。将来のCodex接続・設定を今回新設しない。

1. 変更前に影響範囲、受入条件、漏洩やデータ改変のリスク、戻し方を記録する。Pagesの自動プレビュー設定を先に読む。未承認の修正コミットには[CF-Pages-Skip]を先頭に付け、is_skippedを確認する。ブランチを作るだけでも基点コミットのプレビューができる場合がある。preview_deployment_setting=noneを確認済み。今後の作業前にも読み取り確認し、変更されていれば公開を伴う保存前に止める。作業は最新mainからtask/<短い目的>またはfix/<短い目的>のブランチで行う。
2. 重要な動作・依存・CSP・公開設定の変更は小さいPRにする。差分、CSVへの影響、費用/権限、テスト結果、未検証事項、復旧手順を記載。PR #2を再利用・マージしない。
3. 最低限 `node tests/core.test.js` と `node tests/app.test.js`。変更に応じて悪意ある入力・容量境界・文字コード・出力・スマホ・Analytics互換性を検証。通過だけで「安全確認済み」とはしない。
4. 差分レビューで入力の外部送信、危険なDOM挿入、数式、秘密、依存、権限・課金を確認。重要変更は人間の承認を待つ。低リスク文書は自律更新可。テスト失敗・必要な検証不足のままマージしない。
5. マージ後、Pagesの成功コミットと公開HTTP/機能を確認。障害時は直前の良好なコミットへrevertするPRを作成し、権限を増やして管理画面から無理に復旧しない。緊急時は影響と必要な承認を報告する。
6. 作業終了時は本ファイルと当月記録を更新。変更ファイル・コミット/PR・確認日時/方法・残存リスク・次の判断・承認待ちを残す。実測が得られたときだけkpi.csvの空欄を埋める。
