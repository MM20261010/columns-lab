## 最小仕様と検索入口

入力は予定名、開始/終了日、曜日1つ、同日内の開始/終了時刻、日本時間、明示的な除外日、系列ID。2000〜2099年・最大366日・予定名200文字・除外最大53件。繰返し1系列のRRULEとEXDATEを持つUTF-8 ICSを返し、実際に含まれる日付一覧/件数も返す。日またぎ、終日、複数曜日、祝日自動判定、外部データ取得、既存予定の更新・削除・同期は対象外。DTSTAMPは呼出し時刻、テストでは固定値を注入できる。

候補検索語：「毎週の予定 ICS 除外日」「定期予定 カレンダー 一括 休み」。検索流入や紹介先は未実証。将来の入口1ページは「期間と曜日→除外日→日付一覧の確認→ICS保存→PCの公式読込み手順」の順。Google公式のPCインポート説明に沿い、スマホだけでの取込みを保証しない。自前の登録APIやアカウントは不要。

既存カレンダーやAIでも代替可能。選ばれる理由は「日本時間と除外日を入力して、実日付一覧を先に確認できる」という仮説であり、独自機能の証明ではない。AIに与えるための大量の予定情報を集めない。実予定を当リポジトリへ記録しない。

## 実行した成果

- `node --test experiments/schedule-ics/core.test.cjs`：12件合格、0失敗。
- 日付と除外、JST→UTC、0時の日付跨ぎ、先頭除外、重複除外、不正日付/時刻/期間、全件除外、閏日、プロパティ注入対策、UTF-8の75オクテット折返しと復元を確認。
- `synthetic-example.ics` を実生成：386 bytes。11月の毎週月曜18〜19時、11/23除外、11/2・9・16・30の4回。合成データのみ。
- 独立したGoogle/Outlook/Appleカレンダーへの読込み、ブラウザ表示/保存、Android実機、更新時の重複挙動は未検証。12件のNode試験を利用者獲得・インポート成功と同一視しない。
- 個人情報、アラーム、参加者、添付、外部URLを出力へ追加しない。UIDは呼出し側が継続して保持する系列IDを使うが、同じUIDならどのアプリでも重複しないとは保証しない。

## 次の判定と停止条件

現時点では**公開候補への転換準備**まで。画像より集客力が高いと実測で確認したわけではない。需要不明のままWeb UIや新サイトを増やさない。

次にICS開発を進める条件は、対象検索意図に対する未充足の一次利用者事例、または既存接点からの利用意向を少なくとも1件確認でき、公開前に合成ICSの独立した取込検証が通ること。取得できなければコアを凍結し、機能を増やさない。この1件は探索ゲートで、事業成功数値ではない。アカウント作成・外部投稿・ユーザーへの直接連絡は未承認なので行わない。

仮に公開を承認された場合だけ、14日間の当該ページの測定が正常で、非QAの30PVと検索クリックまたは参照元の独立した流入信号を判定する。閾値は事前の判断基準で需要予測ではない。未取得は不明、PVは変換完了と区別する。未達なら追加開発停止。11/30の全体1000PV目標とは別で、同目標を達成したとは報告しない。本人への反復転記・個別カレンダーサポートを前提にしない。
